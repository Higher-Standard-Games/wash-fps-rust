# v1.0.0-beta13 papercuts

An overnight pass over the native client (wash-fps-rust) and the engine
(shagger), looking for performance, data flow, file size, security, privacy,
latency and bug papercuts. Each row is either **fixed** (merged to `main`) or
**proposed** (found, measured or reasoned about, but left for a decision
because it changes a format, a release step or player-visible behaviour).

PRs: shagger [#25](https://github.com/Higher-Standard-Games/shagger/pull/25) and
[#26](https://github.com/Higher-Standard-Games/shagger/pull/26), wash-fps-rust [#32](https://github.com/Higher-Standard-Games/wash-fps-rust/pull/32) and #33, wash-fps [#13](https://github.com/Higher-Standard-Games/wash-fps/pull/13). Rows 12 to 16 are the second round (RUST.md, "Beta13 papercuts, second round").

## Matrix

| # | Area | Finding | Severity | Status | Where |
| --- | --- | --- | --- | --- | --- |
| 1 | Security, privacy | The account key (the account's only credential) was written with the default umask, so other users on a shared machine could read it (0644). | High | Fixed: written 0600 with `write_atomic_private`; an existing key file is tightened to 0600 by `restrict_to_owner` before it is read. | shagger `core/atomic_file.rs`; wash-fps-rust `client/lobby_panel.rs`, `main.rs` |
| 2 | Security | "Save key file" built the file name from the player name. A name with `/`, `\` or `..` could write outside the chosen folder. | Medium | Fixed: `key_file_name` keeps only letters, digits, `_` and `-`; test `a_key_file_name_stays_in_its_folder`. | wash-fps-rust `client/profile_view.rs` |
| 3 | Security | HTTP fetches followed every redirect, including https to http, so a redirect could move a download (update index, levelshots, demos) off TLS. | Medium | Fixed: redirects that leave https are refused and chains stop after 10; test `a_redirect_is_followed`. | shagger `network/client/http_fetch.rs` |
| 4 | Security, performance | The update index, levelshots and demo downloads had no size cap, so a bad or hostile server could fill memory. | Medium | Fixed: `HttpFetch::start_at_most`; caps are 64 KiB for the index, 8 MiB per levelshot, 256 MiB per demo. | shagger `http_fetch.rs`; wash-fps-rust `update_check.rs`, `client/levelshots.rs`, `client/demo_download.rs` |
| 5 | Bug | A failed atomic write or rename left a `.part` file next to the target. | Low | Fixed: the part file is removed on failure; test `a_failed_write_leaves_no_part_file`. | shagger `core/atomic_file.rs` |
| 6 | Performance, data flow | `SnapshotFeed::push` extracted the snapshot's entities twice per snapshot (once for the buffer, once for the history). | Low | Fixed: extracted once and cloned. | wash-fps-rust `client/snapshot_feed.rs` |
| 7 | Bug | `washoi bench --size WxH` was parsed but ignored, and the usage line did not list it; every bench ran at 1280x720. | Low | Fixed: `window::request_size`; checked with `--size 640x360`, which the report now prints. Usage and RUST.md 21.13 updated. | wash-fps-rust `window.rs`, `view/start.rs`, `main.rs` |
| 8 | File size | `view.rs` was 4494 lines. | Maintenance | Fixed: split into `view.rs` (1063), `view/map_renderer.rs` (1931), `view/build_renderer.rs` (814), `view/start.rs` (711). No behaviour change. | wash-fps-rust `src/view/` |
| 9 | File size | `client/lobby_panel.rs` was 3263 lines. | Maintenance | Fixed: `lobby_panel.rs` (1800), `lobby_panel/panel_ui.rs` (1346), `lobby_panel/campaign_tab.rs` (143). | wash-fps-rust `src/client/lobby_panel/` |
| 10 | File size | `window.rs` was 2701 lines. | Maintenance | Fixed: `window.rs` (1082), `window/input.rs` (640), `window/redraw.rs` (1010). | wash-fps-rust `src/window/` |
| 11 | File size | `match_lobby_view.rs` was 2560 lines. | Maintenance | Fixed: state and logic stay in `match_lobby_view.rs` (724); drawing moves to `match_lobby_view/match_lobby_draw.rs` (1847). | shagger `ui/components/` |
| 12 | Security | The self-update index (`latest.json`) and its SHA-256 come from the same server. Anyone who can change the release assets can change both, so the hash proves integrity in transit but not origin. | High | Fixed: the release job signs each package (Ed25519, secret `UPDATE_SIGNING_KEY`) over its name, size and hash; `client-release.sh` carries the signature into `latest.json`; the game refuses a self-update without a valid one (`UPDATE_KEYS`). | wash-fps-rust `update_check.rs`, `release.yml`; wash-fps `client-release.sh` |
| 13 | Latency | The swapchain used wgpu's default frame latency (2) with no way to lower it. | Medium | Fixed: `r_frame_latency` (1 to 3, default 2) sets `desired_maximum_frame_latency`; a match applies a change at once. 1 shows each frame about one frame sooner. | wash-fps-rust `window.rs`, `settings_model.rs` |
| 14 | Performance | Levelshot JPEG decoding and reading a cached demo ran on the game thread. A 2560x1440 levelshot took about 40 ms to decode (release build), a dropped frame or two per map card. | Medium | Fixed: reading, fetching, decoding and saving run on a thread per levelshot or download; starting one takes 0.05 ms. | wash-fps-rust `client/levelshots.rs`, `client/demo_download.rs` |
| 15 | Security, performance | The WebSocket clients accepted messages up to tungstenite's default of 64 MiB. Snapshots and lobby messages are tens of kilobytes. | Low | Fixed: 4 MiB per message and frame on both sockets; test shows an oversized message ends the connection. | shagger `network/client/tls.rs` |
| 16 | Bug | main's `Cargo.lock` named a local shagger path instead of the pinned revision. CI's unlocked build accepted it; the release's `--locked` build would have failed at the next tag. | High | Fixed: the lock names the revision again, and CI's `check` job runs `cargo fetch --locked`. | wash-fps-rust `Cargo.lock`, `ci.yml` |

## Checked and fine

- Nagle is already off on game sockets.
- Downloaded package names are validated before they touch the disk.
- No `unwrap` on data read from the network in the paths reviewed.
- The crash report carries no key, ticket or name.
- CPU frame cost is low. The baseline bench on `dm5` (1280x720, llvmpipe) takes
  about 3.6 ms of CPU per frame (feed 0.62, scene 1.0, prepare 0.38, encode
  0.76, submit 0.84 ms). The GPU, here a software one, dominates, so CPU-side
  optimisation has little to gain until it is measured on real hardware.
